# Работа с видео: анализ кадров и промты

Страница `/projects/:projectId/video` открывается из карточки проекта, когда
раскадровка подтверждена и есть актуальное готовое изображение. ИИ анализирует
кадры и готовит промты движения. Генерация видео, загрузка MP4 и экспорт видео
в DaVinci не подключены.

## Данные и API

`Project.videoPlan` хранит настройки кадров по существующим `frameId`. Старым
проектам миграция не нужна: GET возвращает пустой план с кадрами раскадровки.
Сохранение создаёт черновик, увеличивает `revision` и `editVersion`, очищает
`confirmedAt`. Утверждение требует актуальной структуры, хотя бы одного выбранного
кадра и готового непустого промта у каждого выбранного кадра.

- `GET /api/projects/:id/video-plan`: план, кадры, номера блока/кадра, текст,
  доступность актуального изображения и защищённый preview URL, длительность,
  безопасные метаданные видео. Файловые ключи и operationId не возвращаются.
- `PATCH /api/projects/:id/video-plan`: `{ expectedEditVersion, frames:
  [{ frameId, selected, videoPrompt, promptStatus? }], instructions? }`. `frames` — частичная
  правка, пропущенные кадры сохраняются. Можно передать один кадр.
  Неизвестные/повторяющиеся ID и лишние поля отклоняются с 400; чужой проект —
  404; конфликт версии или изменение раскадровки во время запроса — 409.
  Обновление атомарно проверяет пользователя, версию и снимок раскадровки.

Состав плана при чтении согласуется с текущими ID раскадровки. Удалённые кадры
не возвращаются, новые получают начальные значения; ID никогда не генерируются.
Изменение revision или значимых данных раскадровки делает план `stale`.
На странице несохранённые правки остаются при переключении кадров; при конфликте
можно обновить серверные данные и проверить свои локальные правки перед записью.

Длительность рассчитывает существующий `timelinePlan` из davinciXmlService:
24 FPS, 15 символов/секунду для оценки, точная длительность MP3 при наличии.
Для старого MP3 длительность читается в память тем же анализатором, что в экспорте.
Последний кадр получает остаток без накопления округлений. Некорректная структура
не заменяется другим алгоритмом: API возвращает `timingErrorCode` и null.
Настройки FPS конкретного будущего генератора могут потребовать иной профиль;
текущие параметры явно возвращаются в `timingSettings`.

`StoryboardVideo` содержит только метаданные и ключ файла, уникальный индекс
`userId + projectId + frameId`. MongoDB не содержит бинарное видео.
`inputFingerprint` версии 1 учитывает кадр, видеопромт, исходное изображение,
длительность, профиль и провайдера, но не общую revision раскадровки.
Будущий генератор должен сохранять этот fingerprint из точного снимка входов.
Изменение другого кадра или служебного updatedAt изображения само по себе не
делает видео устаревшим. Изменение распределения длительности влияет только
на кадры с изменившейся целевой длительностью. GET вычисляет эффективный статус
`stale`, не изменяя запись готового видео. Старые MP4 автоматически не удаляются.

## Файлы

`storyboardVideoStorage` использует папку `video` проекта, локальную либо Drive,
и имя `video_<номер блока>_<номер кадра в блоке>.mp4`.
Локальный projectPath должен уже существовать; сервис не перемещает другие медиа.
Пути проверяются по строгому шаблону, символьные ссылки в video и на файл
отклоняются. Проверяется MP4-контейнер ftyp; это не полная проверка кодека.

Контракт будущего генератора: сериализовать операции для одного целевого имени;
`saveStoryboardVideoFile` → записать метаданные в БД → `commitStoryboardVideoFile`.
При ошибке записи БД вызвать `rollbackStoryboardVideoFile`. Локальная запись
заменяется атомарным rename с резервной копией для отката. Drive создаёт новый
файл и удаляет предыдущий только на commit (передать `previousStorageKey`).
Сбой cleanup после commit не должен вызывать rollback уже записанной БД.
Сбой процесса между файловой записью и БД может оставить временный файл/копию;
распределённая транзакция Drive/MongoDB не заявляется. Перед подключением
генерации потребуются обработка зависших операций и лимиты размера провайдера.

Чтение/удаление принимают доверенный storageKey из принадлежащей пользователю
записи, а не из тела запроса. Публичных endpoints загрузки/чтения MP4 пока нет.

В Settings редактируются `videoPlanAnalysisPrompt` и сохранённый
`videoPromptPreparationPrompt`. Старые клиенты при сохранении сохраняют эти поля.
Тесты покрывают схему, владение, частичные правки, конфликты, fingerprint,
таймлайн, имена, пути, локальные commit/rollback и символические ссылки.
Живой Google Drive и визуальная проверка на телефоне требуют ручной проверки.


## ИИ и массовая подготовка

Все POST `/api/projects/:id/video-plan/:action` принимают `expectedEditVersion`:

- `analyze-start`: отдельный короткий запрос ИИ определяет лимит кадров
  и допустимые блоки из инструкции. Начинает новый анализ, сбрасывает выбор и оценки; тексты
  промтов сохраняются до обработки соответствующих кадров.
- `analyze` + `chunkIndex`: анализ одной серверной части из `analysisChunks`,
  возвращаемых GET. Части сгруппированы по блокам озвучки, максимум 8 кадров
  и около 24 000 символов исходных данных. Общий промт ограничен 70 000 символов;
  слишком большой одиночный кадр/набор референсов отклоняется до вызова провайдера.
- `prepare` + `frameId`: один выбранный кадр с актуальным изображением.
- `reset`: сброс статуса только выбранных кадров; текст промтов сохраняется.
- `confirm`: утверждение плана без изменения исходных материалов.

Анализ возвращает строго проверяемые ID, selected, importanceScore (0–100)
и черновые videoPrompt. После каждой части сервер выбирает лучшие оценённые
кадры в пределах общего лимита. Поздние части могут заменить выбор ранних.
Лимит действует на всю указанную область, а не заново на каждую часть. Если подходящих
кадров меньше, выбирается меньше лимита. Без числового ограничения сохраняются
все подходящие кандидаты ИИ.

`videoPlan.analysis` сохраняет лимит, allowedBlockIds (null — все блоки)
и номера обработанных частей. ИИ получает каталог блоков с ID, номерами,
названиями и числом кадров. «Выбери только 3 кадра в первом блоке» задаёт
лимит 3 и ID блока номер 1. Сервер отправляет на анализ только части этого
блока и исключает остальные блоки из выбора. Списки и диапазоны блоков также
интерпретируются через каталог; неизвестные и повторяющиеся ID отклоняются.
Новый анализ пересматривает весь выбор: кадры вне указанной области снимаются
с анимации, их промты остаются сохранёнными.

Анализ можно
продолжить после остановки или перезагрузки. Ручное изменение выбора, промтов
или инструкций сбрасывает возможность продолжения; изменение раскадровки
также требует нового анализа.

Ручной начальный промт сохраняется с promptStatus=pending. Детализация делает
его ready. Редактирование уже готового промта сохраняет ready. API принимает
явный promptStatus=pending/ready; для старых клиентов без этого поля сохранено
прежнее поведение.
Детализация использует текстовый AI-профиль пользователя и возвращает только
английский промт движения. Неизвестные ID, неполные части и некорректные ответы
отклоняются целиком, ранее сохранённые части остаются в БД.

Клиент вызывает отдельный endpoint для каждой части/кадра. Продолжение пропускает
готовые непустые промты. После перезагрузки сохранённые статусы загружаются из БД;
автоматическое возобновление платных запросов не выполняется. Остановка ждёт
текущий запрос и запрещает следующий, включая повторы после rate limit.
Retry-After поддерживает секунды и HTTP-date; без него используется экспоненциальная
задержка (не более четырёх повторов). Закрытие страницы прерывает клиентскую очередь,
но уже отправленный серверный запрос может закончиться и сохранить результат.

Каждый результат записывается атомарно с проверкой владельца, editVersion и
снимков раскадровки, озвучки и референсов. При конфликте запись отклоняется;
локальные ручные правки можно сохранить при обновлении данных и проверить снова.
Сохранение кадра меняет только этот кадр; отмена правок также локальна кадру.
Общие инструкции сохраняются автоматически перед запуском ИИ либо отдельным
действием и передаются в оба вида промтов. Перед одиночной детализацией также
сохраняются правки текущего кадра. Остальные кадры при этом не меняются.

## Работа со страницей

1. «Выбор кадров»: задайте инструкции и нажмите «Анализировать и предложить
   кадры» либо самостоятельно отметьте «Анимировать этот кадр». Можно написать
   черновик движения и сохранить его без обращения к ИИ.
2. «Детализация промта»: обработайте текущий кадр или все выбранные.
   «Продолжить детализацию» пропускает готовые промты. Остановка завершает
   текущий запрос и сохраняет его результат.
3. Проверьте результат и при необходимости утвердите план кнопкой в общей панели.

Все общие действия находятся в одном горизонтальном ряду возле анализа:
массовая детализация, продолжение, запуск заново и утверждение. Панель
прокручивается по горизонтали, если кнопки не помещаются. Одиночная детализация
остаётся у текущего кадра.

Панель отдельно показывает общее число кадров, выбранные для анимации и готовые
к генерации. Готовность требует выбора, ready-промта, актуального изображения
и доступной длительности. Несохранённые правки и устаревшая раскадровка не
считаются готовыми. Число выбранных и цвет номеров учитывают локальные галочки.

Список кадров содержит только номера без миниатюр. Кадры для анимации выделены
зелёным, текущий кадр — дополнительной рамкой. Фильтр «Все кадры / Только с
анимацией» действует на список и навигацию «Предыдущий / Следующий», сохраняя
исходную нумерацию. Кадры с несохранёнными правками остаются доступны до
сохранения или отмены, даже если галочка снята. Звёздочка обозначает
несохранённую правку. Прогресс ИИ подписан названием операции и скрывается
после её завершения.

Серверные тесты используют имитацию ИИ и БД. Интерфейс дополнительно проверен
в локальном Chrome с тестовыми ответами на ширинах компьютера и телефона.
Живой вызов провайдера требует отдельной проверки.
